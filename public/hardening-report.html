Reliability report

Research Agent Hardening

A Next.js research agent running on LangGraph and Groq. The first version I shared hit rate limits, hung on failures, and showed raw errors. Here is what I found and fixed. Every number below is measured, not estimated.

2,917 Input tokens per heavy turn, from Groq's own counter
10 / 10 Turns clean in a realistic conversation test
350 ms Rate-limit response, was 26 seconds of silence
6 Security issues found and fixed
01 · Diagnosis

The obvious cause was the wrong one

The assumption was that web search results were flooding the model's context. I measured the real request instead. Search results were 11% of the budget. The system prompt was 55%.

Input cost per request, measured with Groq's prompt_tokens
ComponentTokensShareSuspected?
System prompt419 × 3 calls55%No
Memory summary61 × 3 calls12%Yes
Tool definitions302 × 3 calls11%No
Web search results~160 each11%Prime suspect
Why. LangGraph resends the whole message history on every step of the agent loop. A two-tool question is three model calls, so every fixed token gets charged three times. Trimming search results, the intuitive fix, could not have solved this.
02 · Models

Both halves of the loop have to be tested

A model has to do two separate things: emit a valid tool call, and write an answer once the tool returns. Passing one says nothing about the other. I found that out after shipping a model that scored 5 out of 5 on tool calls and then returned blank answers.

03 · Throughput

What changed

  • System prompt compressed. Cut repetition and justification text, not instructions. An automated check confirms all 20 behavioural rules survived the edit.
    3,619 chars→1,900 chars
  • Model fallback chain. Each Groq model has its own quota, so a rate limit now retries on the next model instead of failing. This also survives a daily cap, which waiting cannot fix.
    8K tokens/min→16K pool
  • Cooldown cache. Real retry-after values are recorded per model, so a request during a limit window answers straight away instead of spending 8 seconds per model rediscovering the block.
    26,000 ms→350 ms
  • Search budget capped at 3 per turn, in code. The model was making 8 or more searches for one question and burning 23.9K tokens before running out of steps. A prompt rule was not enough, so the tool itself now refuses past the budget.
04 · Failures

Failures degrade instead of breaking

  • Rate limits arrive as normal messages with the real wait time, never an error screen.
  • Daily and per-minute limits are told apart. Saying "retry in 13 seconds" when the daily cap is gone is worse than saying nothing.
  • Malformed tool calls are caught using Groq's tool_use_failed code, not by matching error text. The wording changed four times during this work. The code never did.
  • Step-limit exhaustion keeps whatever the model produced and explains the stop, instead of throwing the run away.
  • Empty answers count as a failure and move to the next model, rather than rendering an empty bubble.
  • Invented tool parameters no longer crash. The model made up four different ones across traces, so the schema now accepts and ignores unknown keys.
05 · Security

Six issues found in review

  • Remote code execution in the calculator. Model output was passed to Function() behind a character allowlist, one missed character away from arbitrary execution. Replaced with a parser that can only return a number. Verified against 13 attack strings, all blocked.
  • SQL filter injection in knowledge-base search. The PostgREST .or() filter was built by string concatenation with untrusted input, so a crafted query could match every row. Metacharacters are now escaped.
  • Four input fixes. Unbounded message input (now capped at 4,000 characters), unguarded JSON parsing, unvalidated session IDs, and database errors leaking to the client.
06 · Interface

Waiting, and mobile

  • Progress is visible. A search-heavy answer used to show nothing for 17 seconds. Status now appears at about 1 second and says what is happening, including when a backup model is being tried.
  • The input locks when it has to. If every model is limited, the composer disables with a live countdown and re-enables itself, instead of letting you send something that cannot work.
  • Answers stopped cutting off mid-word. A full 9-day itinerary needs about 1,234 output tokens and the cap was 800. Raised to 1,500, with the caveat text limited to one line, the same answer now finishes in 913.
  • Mobile layout fixed. iOS zooming on input focus, the composer sitting under the home indicator, 100vh pushing it off screen, 36px tap targets, and long URLs forcing sideways scroll. Checked at 360px and 390px.

08 · Open

Known limits

  • The free tier is the real ceiling. About 2,900 input tokens per heavy turn against 8,000 per minute per model works out to roughly 2 to 3 demanding questions a minute. Only a paid tier changes that.
  • No auth or per-user rate limiting on the API routes. That matters for a public deployment, not a demo, and it is a design decision rather than a quick patch.
  • Occasional LaTeX in answers. The markdown renderer has no math support, so a stray formula shows as source. Diagnosed, cosmetic, deliberately left for later.
  • State is in memory. Cooldown and token tracking are per instance, not shared across serverless workers.
